# 割接等待不是光纤往返时延

本文是同目录英文稿的简体中文版，英文原文保持不变：[A cutover wait is not a fiber round trip](cutover-wait-versus-fiber-delay.md)。

## 要做的判断

一条城域链路是 27 km 光纤，同一天下午还计划做 DNS 变更。工单里会出现两只钟：解析器还可能保留旧记录多久，以及数据包在光纤上花多久。二者都叫“时延”。它们不是同一个时延。把它们相加，得不到维护窗口。

## 每个工具管什么

DNS TTL 计算器在没有 `peakOldTtl` 的基线路径上，把旧 TTL 和已经过去的时间换成剩余、典型和最坏分钟，以及每日查询比。光纤时延计算器把距离和群折射率换成微秒级传播时间。两个引擎都不读取对方的输出。

## 一张工单，两种单位

| 输入 | 取值 | 工具 |
|---|---|---|
| 旧 TTL、新 TTL | 7200 s，300 s | DNS |
| 已过时间、权威侧延迟、负缓存 TTL | 1800 s，20 s，300 s | DNS |
| 提前降低 | 48 h | DNS |
| 距离、路由系数、群折射率 | 27 km，1，1.468 | 光纤 |
| 设备与串行化 | 无 | 光纤 |

群折射率 1.468 和 \(c = 299792.458\) km/s 是时延引擎的常数。DNS 的分钟显示是一位小数，`round((seconds/60 + ε) × 10) / 10`。

## 两只钟分开算

剩余缓存时间：

$$
t_{\mathrm{left}} = \max(7200-1800,\ 0) = 5400\,\mathrm{s} = 90.0\,\mathrm{min}
$$

典型等待 = \(0.5\times 5400 + 20 = 2720\,\mathrm{s}\)，显示 45.3 min。最坏等待 = \(\max(5400,\ 300)+20 = 5420\,\mathrm{s}\)，显示 90.3 min。每日查询从 \(86400/7200 = 12\) 变为 \(86400/300 = 288\)，倍数为 24。48 h 的提前降低窗口长于 7200 s，所以基线状态保持 `pass`。

光纤单向传播：

$$
t_{\mathrm{prop}} = 27 \times 1.468 \times \frac{10^{6}}{299792.458} = 132.211\ldots\,\mu\mathrm{s}
$$

引擎的显示规则（低于 1000 µs 时两位小数）印出 **132.21 µs**。往返是它的两倍，**264.42 µs**。没有加入设备时延，也没有加入串行化。

## 为什么这两个数碰不到一起

90.0 分钟是 \(5.4\times 10^{9}\) 微秒。光纤 RTT 是 264 µs，大约是剩余 TTL 的两千万分之一。把 264.42 µs 加到 90.0 min 上，不会改变显示出来的分钟，也不会改变查询比告警。割接要按它安排的等待，是这条基线上 DNS 的最坏情况，90.3 min。光纤数字回答的是另一个问题：解析器一旦再次查询，路径时延是不到一毫秒，而不是又一个小时。

即使群折射率有误，27 km 的 RTT 仍是亚毫秒。如果旧 TTL 没有提前降低且已过时间为 0，剩余缓存就是完整的 7200 s。这个变化让 DNS 的钟移动若干小时，并不移动光纤的钟。

## 限制

- 只有 DNS 基线。`peakOldTtl` 字段会打开本篇没有使用的第二种情景。
- 光纤距离是你输入的路由公里，不是实测 OTDR 曲线。
- 两个结果都不是“每台解析器都已过期”或“光路健康”的承诺。损耗和色散是另外的工具。
